# ztecfg 虚拟分区

## 调查依据

指定固件的 `/vendor/bin/variantid` 包含两个分区路径：先访问 `/dev/block/bootdevice/by-name/ztecfg`，失败时访问 `/dev/block/by-name/ztecfg`。静态检查表明其以只读方式打开，定位到偏移 4096 后读取 24576 字节。服务配置位于 `/vendor/etc/init/zcustom.rc`。这些是源码和固件的静态调查结果，尚未验证模拟器内服务实际运行或限定主题生效。

## 导入与重建

1. 保留原始固件包和 `ztecfg.img`。复制原来的六条目目标固件 ZIP，使用支持 ZIP64 的压缩工具向副本的根目录添加 `ztecfg.img`；不要放在子目录，也不要添加同名重复条目。镜像必须为 524288 字节。
2. 使用修改后的 ZIP 新建导入实例。导入器在私有实例中复制镜像，并使用根目录内的固定相对符号链接将上述两个 Guest 路径指向同一份副本；原镜像不受 Guest 写入影响。该副本不会提供真实块设备的完整接口。
3. 固件和配置可能含设备数据，不要将 ZIP、镜像或未脱敏内容提交到 Git 或公开分享。

不含该条目的旧格式 ZIP 仍可导入。该方法只适用于新导入实例，不会为已有实例补入分区；克隆行为未验证。

## variantid 启动

正常启动时，针对 NX809J、Android 16/API 36、ARM64 固件，在持久属性加载、属性服务与链接器配置就绪后，以及框架服务启动前，受限执行一次固件自带的 `variantid`。启动前检查原厂服务声明、触发动作和实例内两个分区路径（包括相对链接的目标及父目录）；未满足条件则不执行。该适配不启用其他 `oneshot` 服务。

执行会等待结果并限制等待时间。非零退出码会如实记录；无法确认执行结果时中止本次框架启动。日志不记录程序原始输出。退出码为零也不能证明配置读取成功：固件可能使用默认版本标志。此处仅完成启动适配和自动化测试，尚未验证 Guest 实际运行、属性结果或限定主题生效。

## 主题属性和资源选择

对指定固件的静态检查显示，原厂 `init` 在早期查询 `zte_variantflag`，默认使用 `GEN_CN`，并通过 `TRANSFORM_HW_FLAG` 选择 `/system/carrier/projects/<版本>/prop_fixed.txt`；项目目录缺失时回退到 `GEN_CN`。鸣潮项目包含主题、桌面和铃声等配置，其对应主题和桌面资源也存在于固件中。

RedMagicEMU 不运行原厂 `init`。现有适配仅对 NX809J、Android 16/API 36、ARM64 且提供私有 `ztecfg` 的实例，在属性服务准备时解析配置中的首条匹配记录并选择项目，先填普通启动默认属性，再覆盖项目属性，然后恢复已保存的持久属性，最后应用运行时覆盖。属性文件只接受指定固件三个项目 `GEN_CN`、`IP_PB_CN`、`IP_MC_W_CN` 已核实的 14 个属性键；遇到未知键、格式错误、不安全路径或读取失败时报告错误并中止启动。没有 `ztecfg` 的旧实例不加载项目配置，保持原有属性处理。找不到版本记录或对应项目目录时回退 `GEN_CN`；默认项目或属性文件缺失则报告错误。

作为额外的一致性保护，在 `variantid` 尝试运行之后、框架服务启动之前，会比较实际属性区的 `persist.vendor.custom.variant.id` 与选中的项目；缺失或不一致会中止本次启动。该检查是模拟器的保护措施，不代表已证实原厂有同样的失败策略。属性也可能已经由项目文件提供，因此值一致不能证明 `variantid` 已运行或成功读取分区。

固件的鸣潮和另一限定版壁纸 overlay 使用相同包名。对指定固件 `framework.jar` 的静态检查显示，原厂 `OverlayScanner` 读取版本属性，并用 `/system/carrier/CustomAppsList.txt` 和项目 `apps.txt` 筛选候选 APK；鸣潮项目表包含鸣潮版本而不包含另一限定版本。依据该静态逻辑，本次不改动或移除 overlay APK。原厂扫描器能否在 Guest 中正确读取属性和列表、实际选中的包及主题显示仍未运行验证。

电脑端另外使用真实的三个项目属性文件与合成 `ztecfg` 验证生产解析器：三个项目均被正确选择，未知项目回退到 `GEN_CN`。将原厂 `OverlayScanner` 转换为 JVM 字节码并以属性和日志桩运行时，鸣潮项目保留鸣潮 overlay、跳过另一限定版；另一限定版结果相反，普通项目跳过两者。普通项目列表无法从镜像读取，实验以空列表模拟其缺失时的行为。这些实验不验证 Android Guest 的属性服务、包扫描或主题显示。

进一步的电脑端串联实验使用合成分区、生产项目解析器和属性区，再调用转换后的原厂扫描方法；三个项目均得到预期的 overlay 筛选结果，旧版本属性不一致时被检查拒绝。属性服务写入及 Android 接口由测试模拟，不能证明真实 Guest 的服务启动或主题显示。

电脑端还通过 QEMU 运行了指定固件的原厂 `idmap2`，以固件的 `framework-res.apk` 和鸣潮壁纸 overlay 创建并检查资源映射，映射包含 `default_wallpaper` 和 `default_wallpaper_component`。实验保留 overlayable 检查：只提供 public 策略时失败，提供 public 和 signature 策略时成功；两 APK 的签名一致。这不能验证 Guest 中的策略判定、idmap 服务或壁纸显示。

电脑端隔离实验使用 QEMU/PRoot 运行原厂 `variantid` 和合成配置，属性接口由测试桩替代：配置分别写入 `IP_MC_W_CN` 和 `GEN_CN` 时，捕获的 `persist.vendor.custom.variant.id` 分别为对应值，程序均退出 0。该实验不验证 Android 属性服务、RedMagicEMU 启动或主题显示，也不使用原镜像中的设备标识。

另一个隔离实验使用原厂 Bionic、由生产 `PropArea` 创建的合成属性区及测试 socket，捕获到原厂 `variantid` 通过 v2 协议发送鸣潮版本属性。成功与失败对照同时改变了属性区的属主和权限，无法单独确定失败原因。API 36 原生代码的合成文件测试验证了 `fstat` 的属主和可读权限转换；这些实验没有运行 RedMagicEMU 的属性服务或完整路径转换。

## 回滚

代码可通过回退目标项目属性加载和 `variantid` 启动适配恢复原来的属性与服务启动行为；回退相关导入改动可恢复旧导入行为。所有配置均从实例内原厂文件及 `ztecfg` 私有副本重建，不修改原始固件或 overlay APK。使用不含 `ztecfg.img` 的旧格式包重新导入，可创建不含该副本的新实例。当前应用的实例删除功能尚未启用，上述操作不会删除已经导入的实例。
